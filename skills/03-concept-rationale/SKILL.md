# Skill 03 — Concept Rationale

## Purpose
For each of the 4 wireframe concepts, produce a deep, named rationale. Not a description of the layout — the design thinking that makes the concept actionable. Answers: "Why would a real designer choose this direction over the others?"

## Output format per concept

CONCEPT [N] — [Name]

DESIGN HYPOTHESIS
"If [specific user type] [specific belief/behaviour/emotional state], then [specific design approach] will [expected outcome] because [the underlying reason]."
Must be falsifiable — specific enough to be proven wrong by a test.

UX FRAMEWORK
[JTBD or Mental model alignment]
If JTBD: Job + how this concept delivers it differently from the other 3
If Mental model: Reference model + why that model fits this user in this context

PSYCHOLOGICAL PRINCIPLE
Name the principle. Show exactly how the layout/flow decision expresses it.
"This concept uses [principle] by [specific design decision], which means the user [specific behavioural response]."
Principles: completion bias, loss aversion, progressive commitment, familiarity effect, autonomy bias, cognitive load reduction, social proof, reciprocity, endowment effect, anchoring, Zeigarnik effect, scarcity, authority, default bias, peak-end rule, chunking.

SPECIFIC FRICTION ADDRESSED
"The drop-off point this concept addresses: when [specific thing happens], users [specific negative behaviour]. This concept prevents this by [specific mechanism]."

THE BET THIS CONCEPT MAKES
"This concept bets that [specific assumption about motivation/mental state/behaviour]. If wrong — if users actually [alternative behaviour] — this will underperform because [specific consequence]."
All 4 concepts must make genuinely different bets.

COMPETITIVE POSITION
"This concept [follows/challenges/borrows from] [specific pattern from competitive analysis]. It [deviates/does not deviate] in [specific way] because [reason tied to brief and gap]."

A CONCRETE SCENARIO
Real person. Name + location + device + emotional state + time constraint.
Show exactly what they see, what they do, what happens.
4-6 sentences. Not "a user opens the app."

WHAT SUCCESS LOOKS LIKE
2-3 specific, observable, measurable outcomes. Not "users complete the flow."

VALIDATION QUESTION
One question specific to this concept's bet — not a generic usability question.
"The key thing to learn from testing: [question only this concept can answer]."

TRADE-OFF
"This concept optimises for [X] at the cost of [Y]. Accept that [specific non-trivial consequence]."
Real trade-offs: minimal sacrifices discoverability, power user sacrifices accessibility for new users, progressive sacrifices speed for confident users.

## Quality check before outputting

1. Is the hypothesis falsifiable?
2. Are all 4 bets genuinely different?
3. Does the scenario name a real person with real context?
4. Does the trade-off name a real, non-trivial cost?
5. Is the validation question specific to this concept's bet only?

## Rules
All 4 hypotheses must be falsifiable.
All 4 bets must be genuinely different.
All 4 scenarios must name a real person in a real moment.
All 4 trade-offs must name a real, non-trivial cost.
Every section connects back to the structured brief.

## Handoff
When user selects a concept, pass full rationale — hypothesis, bet, scenario, trade-off — to Skill 05.
