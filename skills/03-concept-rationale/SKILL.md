# Skill 03 - Concept Rationale

## Purpose
For each wireframe concept generated by Skill 02, produce a tight, named rationale explaining the design thinking behind it. This is not a description of what is on screen - it explains WHY the concept was designed that way, what framework it applies, and who it is best suited for.

## Output format per concept

CONCEPT [N] - [Name]
Framework applied:    [JTBD / Mental model alignment]
Job or model:         [The specific job or mental model this concept addresses]
Key design decisions: [2-3 specific decisions and why they were made]
Best suited for:      [Which user type, scenario, or team context this fits]
Trade-off:            [What this concept sacrifices to achieve its goal]

## Rules

### Rule 1 - Named, not described
Every rationale must have a concept name that captures the UX direction, not the visual.
Good: "Progressive trust builder"
Bad: "Two-column layout with sidebar"

### Rule 2 - Decisions must be traceable
Every key design decision must trace back to the structured brief or the UX framework applied.
Never state decisions without linking them to a reason grounded in the brief.

### Rule 3 - Trade-offs are mandatory
Every concept optimises for something and sacrifices something else. Name both explicitly.
This is what makes the rationale useful for team decision-making.

### Rule 4 - Best suited for is specific
Do not write "suitable for most users."
Write the specific context: "best suited for first-time users who are anxious about commitment"
or "best for power users on desktop who complete this flow frequently."

### Rule 5 - Keep it tight
Each rationale must be readable in under 30 seconds. No narrative paragraphs. Structured, scannable, direct.

## Handoff
When the user selects a concept, pass the full rationale to Skill 05 (Post-Convergence Handoff) as input context.
